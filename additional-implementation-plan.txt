PHASE 1A — DAEMON AND MULTI-FRONTEND ARCHITECTURE

ARCHITECTURE
[ ] Design project around a headless, independently running daemon
[ ] Keep all NixOS logic independent of frontend frameworks
[ ] Make frontends interchangeable clients of the daemon
[ ] Use Rust and Axum for the daemon's API server
[ ] Design a versioned HTTP/JSON API
[ ] Use WebSockets for live events, progress, and logs
[ ] Publish an OpenAPI specification
[ ] Generate a reusable Rust client SDK
[ ] Make the API usable by non-Rust clients
[ ] Support Unix sockets for local IPC
[ ] Support optional authenticated TCP/HTTPS access
[ ] Implement API capability discovery and version negotiation
[ ] Standardize structured errors and operation identifiers
[ ] Use strongly typed shared API models with serde
[ ] Ensure all clients follow identical authorization rules

FRONTEND FRAMEWORK
[ ] Use Dioxus for the official frontend
[ ] Share UI components, routing, and business logic across platforms
[ ] Build browser frontend using Dioxus Web/WASM
[ ] Build native desktop client using Dioxus Desktop
[ ] Make API base URL and connection transport configurable
[ ] Support local daemon connections from desktop clients
[ ] Support remote daemon connections from desktop clients
[ ] Keep platform-specific logic behind adapter interfaces
[ ] Support browser-based OIDC sign-in
[ ] Support OIDC Authorization Code + PKCE for desktop clients
[ ] Avoid duplicating Nix evaluation logic in frontend applications
[ ] Allow web frontend hosting to be enabled or disabled independently

DAEMON SERVICE
[ ] Create dedicated daemon executable
[ ] Implement NixOS module for installing and configuring daemon
[ ] Run daemon under a dedicated unprivileged system user
[ ] Separate privileged rebuild operations into a helper process
[ ] Provide configurable API listeners
[ ] Add structured logging, health checks, and graceful shutdown
[ ] Store persistent daemon state in a configurable state directory
[ ] Support headless operation without any frontend installed
[ ] Make configuration changes independent of client connections
[ ] Persist long-running operation state and results
[ ] Support multiple concurrent clients
[ ] Serialize conflicting rebuild and maintenance operations

[ ] Support API token or equivalent noninteractive credentials
